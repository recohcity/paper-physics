# Project delivery: from sketch to a runnable interactive app

This file defines WHAT gets delivered and HOW a new sketch project is scaffolded. The goal: the user
installs the skill, drops in a sketch, and gets a complete interactive application (not a demo page) —
the same industrial experience as the reference trebuchet build, with the mechanism swapped.

## 1. The sketch is a first-class asset

The user's uploaded sketch is not consumed and thrown away. It has two jobs:

1. **Intake reference** (workflow step 0-2): the vision model reads it for recognition.
2. **In-scene texture**: it is processed into a texture on the A4 paper sheet lying on the desk, so the
   user sees their own pencil drawing in the 3D scene.

Storage: every new project saves the original sketch at `public/sketch.jpg` (rename per project if
multiple views). The environment renders it on the paper with a "sketch / clean" toggle so the user can
compare the drawn mechanism against the built one.

## 2. Standard project tree

Each sketch becomes an independent, runnable Vite project under `cases/<project-slug>/`:

```
cases/<project-slug>/
├── project.json          # metadata: name, physics domain(s), created date, sketch source
├── spec.json             # the skill Spec (every load-bearing quantity with provenance)
├── public/
│   └── sketch.jpg         # the user's original sketch (intake source + paper texture)
├── index.html            # shell DOM (canvas, panel, tour banner) — copied from template
├── package.json          # vite + three + cannon-es
├── vite.config.js
├── src/
│   ├── spec.js           # single runtime source of truth, generated from spec.json
│   ├── main.js           # App shell: tour/build mode, camera presets, slow-mo, panel wiring
│   ├── environment.js    # desk + A4 paper + pencil + eraser (template, skin-changeable)
│   ├── mechanism.js      # ★ THE ONLY NEW CODE: the mechanism's geometry + physics
│   ├── physics.js        # world, gravity, contact materials (per domain)
│   ├── annotations.js    # hotspots/labels anchored to mechanism meshes
│   ├── textures.js       # procedural + sketch textures
│   ├── audio.js          # optional sound effects
│   └── style.css         # theme
├── docs/                 # auto-generated project record (this project's own folder)
│   ├── report.md         # final delivery report: verdict, assumptions, what was/wasn't modeled
│   ├── verify.log        # headless self-check output (engine vs reference, energy, clip)
│   └── feedback.md       # post-mortem / lessons that feed back into the skill
└── test/
    └── verify.mjs        # headless self-check (see §5)
```

`docs/` is auto-generated by the workflow (step 10) — the report and verify log are written there,
and any pitfall discovered on this project is recorded in `docs/feedback.md`. It belongs to the project,
not to the skill; the skill periodically harvests general lessons from project `docs/feedback.md` files.

**80/20 rule = time allocation, not file count.** What is reused vs what each project writes:

| File | Reused as-is? | Notes |
|---|---|---|
| `index.html`, `src/style.css`, `package.json`, `vite.config.js` | yes | project skeleton |
| `src/main.js` | yes (shell) | render loop, camera presets, tour/build mode, panel framework — calls into Mechanism |
| `src/environment.js` | yes (skin-config) | desk + paper + pencil + eraser; change colors via one config |
| `test/verify.mjs` | framework reused, checks written per domain | structure copied, assertions are project-specific |
| `src/mechanism.js` | **write per project** | the device's geometry + physics |
| `src/spec.js` | **write per project** | this device's parameters |
| `src/physics.js` | write per domain | world/gravity base inherited, contact materials tuned per device |
| `src/annotations.js` | write per project | hotspots anchored to THIS device's meshes |
| `src/textures.js`, `src/audio.js` | write per project (optional) | procedural textures / sounds for this device |

The point: the hard, repetitive startup work — scene graph, camera, UI panel, tour/build flow, desk
environment, build toolchain — is already done. Time goes into the mechanism itself, not into rebuilding
the shell for every sketch.

## 3. The interactive shell (extracted from the reference build)

Every delivered app ships with this shell; it is not optional:

- **Two modes.** *Tour*: auto-plays a narrated walkthrough of how the mechanism works. *Build/Play*:
  the user directly manipulates it. Buttons to switch between them.
- **Interaction panel** (right side): parameter sliders specific to the mechanism's physics domain, a live
  readout table (the measured quantities the feasibility claim rests on), buttons (reset, fire/release,
  equal-mass, etc.). Panel fields are generated from the Spec's `inputs[]` and `outputs[]`.
- **3D navigation**: orbit camera + preset view buttons (hero / side / top / iso), slow-motion toggle,
  flight-path toggle.
- **Desk environment**: wooden table, an A4 sheet showing the user's sketch, a pencil and an eraser
  lying on the paper. Skin points (table material, paper tint, eraser style) are in one config object so
  a project can restyle without touching mechanism code.
- **Annotations**: hotspots/leader-lines anchored to mechanism meshes, not hand-copied coordinates.

## 4. Mechanism interface (the 20% new code)

`src/mechanism.js` exports a class the shell drives. The contract:

```js
export class Mechanism {
  constructor(scene, world, spec) { /* build meshes + bodies from spec */ }
  reset() {}                       // back to rest pose
  cock(angleOrParam) {}            // prepare for the demo action
  release() {}                     // fire / drop / drive
  setParam(key, value) {}          // panel sliders call this
  readout() { return [] }          // rows for the live table
  update(dt) {}                    // per-frame (if the shell doesn't step the world itself)
  dispose() {}
}
```

The shell owns the render loop, camera, mode switching and panel; the mechanism owns only what is
specific to this device. If a new device needs a new control the shell doesn't have, add it to the
shell once (so the next device inherits it) — do not fork the shell per project.

## 5. Project self-check script (`test/verify.mjs`)

Delivered projects must run headless before handoff (principle 8). The script:

1. imports the same physics the browser build uses;
2. runs the reference solver vs the engine on the same inputs and asserts within tolerance;
3. asserts rest state settles as drawn, no body clips a static prop, no body inverts;
4. asserts energy is not injected (kinetic energy never exceeds the input energy after settling);
5. exits non-zero on any failure.

Run with `node test/verify.mjs`. A project is not delivered until this passes.

## 6. Project lifecycle (added to the workflow)

After step 2 (Spec + ambiguity confirmation), before any mechanism code:

- **Scaffold.** Copy `skill/template/` into `cases/<slug>/`, rename, save the sketch to `public/`.
- **Generate `src/spec.js`** from `spec.json` (single source of truth).
- **Write `src/mechanism.js`** for this device.
- **Fill the panel** from Spec inputs/outputs.
- **Run `test/verify.mjs`**; fix until it passes.
- **Record experience** — any new pitfall, shell gap, or domain finding goes to
  `docs/skill-feedback/`; recurring ones fold back into `references/`.

## 7. What "complete" means vs "demo"

A demo stops at: it renders, it moves if you poke it. A delivered application ships:
- the industrial shell (tour + build + panel + navigation + desk),
- every object carrying its correct physics from build time (principle 7-8),
- a passing headless self-check,
- a Spec and a feasibility verdict,
- and runs with `npm install && npm run dev`.

## 8. Tour stage contract (8 steps, verbatim from paper-trebuchet)

Every project's tour follows the same 8 stages. The shell drives them; the
mechanism only provides the meshes/materials for each stage. Do NOT invent a
new stage order.

| # | Stage | What is on screen | What the mechanism must provide |
|---|-------|-------------------|----------------------------------|
| 0 | **READ** | Only the A4 paper with the user's sketch (centered, ~50% scale). Pencil + eraser on desk. No 3D model. | paper texture with sketch drawn on it (cream `#f7f4ea` bg) |
| 1 | **LIFT** | Sketch outline fades in as a 2D cutout lying flat on the paper, then rotates `-PI/2 → 0` to stand up vertical. Camera: Side. | A `PlaneGeometry` mesh whose material is the sketch cutout (white bg removed, transparent). Starts flat on paper, stands up. |
| 2 | **MODEL** | 2D cutout fades out; white (untextured) 3D model morphs in. Camera: Side. | The 3D group with all meshes in white/gray material. `visible=false` until this step. |
| 3 | **MATERIAL** (was WOOD) | White model gets its real materials (metal/wood/plastic). | Material swap: white `MeshStandardMaterial` → textured. |
| 4 | **PARTS** | Component labels / annotations fade in pointing at key parts. | Annotation sprites/lines anchored to part world positions. |
| 5 | **RUN** (was FIRE) | The mechanism runs its canonical demo motion automatically. | The physics/animation sequence; camera follows. |
| 6 | **REPLAY** | Slow-motion (0.25×) replay of the run. | Same animation with timeScale=0.25. |
| 7 | **BUILD** | Switch to build mode: user can drag/adjust parameters. | Interactive drag handlers + parameter panel. |

### LIFT cutout rules (learned the hard way)

- The cutout is a **separate mesh** from the paper texture. The paper shows
  the full sketch; the cutout is the same image with white background made
  transparent (use canvas `globalCompositeOperation='destination-out'` to
  knock out near-white pixels, or pre-process the sketch PNG).
- Never put a rectangular sketch.jpg directly on a plane — the white box
  shows. Always matte out the background.
- Cutout starts at `rotation.x = -PI/2` (flat on paper), tweens to `0`
  (vertical). Position it just above the paper (`y ≈ 0.012`).
- At MODEL step, hide the cutout and show the 3D group. Do not leave both
  visible.

### READ paper rules

- Paper is `BoxGeometry(2.7, 0.006, 1.85)` at `(0.12, 0.003, 0)`.
- Sketch is drawn centered at ~50% of paper width, not full-bleed.
- Paper bg is cream `#f7f4ea`, never pure white.
- Pencil at `(-0.05, 0.077, -0.73)`, eraser at `(1.15, 0.006+thickness/2, -0.75)`.

## 9. Refined delivery workflow (v2, from Newton's Cradle pressure test)

Trigger: user uploads a sketch image + @sketch2sim.

1. **Intake** — save sketch to `public/sketch.jpg`, extract mechanism name/scale.
2. **Scaffold** — `skill/template/` copied to `cases/<name>/`, npm install, dev server on 5174+.
   Shell = full tour frame (wood desk, cream paper, pencil, blue-white eraser, bottom panel, hero/side/top/3D views, zoom, REWIND/PLAY/FF).
3. **Tour stages** (button names generalized):
   - **SKETCH** (was READ): sketch scaled ~30%, placed centered on A4 paper. Position MUST pre-plan the later cutout bottom line and 3D model footprint — these align at delivery.
   - **LIFT**: paper sketch disappears; irregular cutout along pencil outline rises IN PLACE about its own bottom edge (pivot = bottom, not center). Bottom edge coincides with sketch bottom.
   - **MODEL**: 2D cutout becomes white 3D model. OFFER TWO PATHS: (a) three.js inline primitives, (b) Blender headless Python export glb. After model appears, HALT and wait for user confirmation.
   - **MATERIAL** (was WOOD): materials + lighting. After done, HALT for user confirmation.
   - PARTS / PLAY (was FIRE) / REPLAY: deferred.
4. **Build mode** — switch to build mode and deepen interaction FIRST. Ask user which parameters the side panel should expose (sliders, buttons, material swaps). Only build what user confirms.
5. Only after build-mode interaction is accepted, circle back to fill PARTS / PLAY / REPLAY in the tour.

Hard rules learned:
- Shell (desk/paper/pencil/eraser/lights/camera/panel) is 100% copied from reference build; never reinvent.
- Every object carries physics from construction (even decorative pencil/eraser) — collisions just work.
- Ropes are inextensible, no spring; hanging points must not penetrate beams.
- Cutout rises in place (bottom pivot), not centered, not scaled.
- After each stage, self-test in browser before showing user.
